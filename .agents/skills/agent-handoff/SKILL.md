# Agent 交接规范

## 目标

生成一份下一个 Agent 可以直接执行、可以核验、不会误解授权边界的持久化交接文件。交接文件记录结论和证据，不复制完整对话，也不暴露隐藏推理过程。

本 Skill 只整理和保存交接信息。除非用户同时明确要求，否则不要借交接之名实施剩余任务、触发 CI、编译、发布、推送、刷写设备或修改外部状态。

## 何时使用

出现以下任一意图时使用：

- 用户要求“交给下一个 Agent”“生成或更新 handoff”“保存上下文”“换会话继续”。
- 当前工作已完成设计或调查，实施、验证或发布要留给后续 Agent。
- 用户希望控制 token 消耗，把高成本工作拆到下一阶段。
- 已有交接文件需要根据新决策、新证据或新状态同步更新。

普通进度汇报、最终答复或临时笔记不需要单独生成交接文件。

## 核心规则

1. **事实优先**：以工作区文件、版本控制状态、命令输出和用户明确决定为准。对无法核实的内容标记 `UNRESOLVED`，不要猜测。
2. **状态分离**：严格区分 `已完成`、`已设计但未实施`、`已授权待执行`、`未授权/禁止`、`验证失败`、`未验证`。
3. **证据对应结论**：只有实际运行且看到成功结果的检查才能写“通过”。中断、失败、未运行和需要 CI/真机验证必须如实写明。
4. **保留边界**：逐项记录用户禁止的动作，例如不触发 GitHub Actions、不编译、不提交、不推送、不刷机。交接不会扩大授权。
5. **保护工作区**：标出用户原有改动、当前任务改动和未知来源文件。不得把未跟踪文件自动当作本任务产物，也不得清理、覆盖或提交秘密。
6. **面向执行**：给出按依赖排序的下一步、读取顺序、精确文件路径和完成条件，避免“继续处理”等模糊描述。
7. **控制篇幅**：只保存后续工作必需的信息。用文件链接或路径指向详细设计，不在交接中重复整份规格。

## 工作流程

### 1. 确认范围与存放位置

先读取仓库的 `AGENTS.md` 和适用的项目 Skill。查找既有 handoff 命名和目录约定；有约定时沿用，没有时使用：

```text
docs/handoffs/YYYY-MM-DD-<topic>-handoff.md
```

同一任务已有交接文件时优先更新原文件，不创建互相冲突的副本。只有缺失信息会实质改变后续方案或权限时才向用户提问；其余情况使用保守假设并显式记录。

### 2. 收集可验证状态

按任务需要检查：

- 用户最新目标、明确选择、保留项、排除项和禁止动作。
- 相关规格、计划、需求源、manifest、配置或源码。
- `git status --short`，必要时查看相关 diff；不要把整个工作区都归因于本任务。
- 已执行验证的完整命令、退出状态和关键结果。
- 失败、中断、外部依赖、需要 CI/硬件/账号才能完成的事项。

不得把记忆中的命令结果写成当前证据。敏感值只写“已配置/未配置”，不要保存密码、token、私钥、Wi-Fi 凭据或现场网络信息。

### 3. 建立状态账本

为每项工作分配且只分配一个当前状态：

| 状态 | 含义 |
|---|---|
| 已完成 | 文件或结果已落地，并有可定位的证据 |
| 已设计未实施 | 已有批准方案，但源码或配置尚未修改 |
| 待验证 | 已实施，但所需检查尚未完成 |
| 失败或受阻 | 检查失败、中断，或缺少必要外部条件 |
| 未授权或禁止 | 用户明确不允许当前或后续 Agent 自动执行 |
| UNRESOLVED | 缺少事实，不能安全决定 |

发现旧交接与当前证据冲突时，更新为当前状态，并在“变更摘要”中简述原因；不要保留两个互相矛盾的现状描述。

### 4. 写交接文件

使用 `references/handoff-template.md` 的结构，并遵守以下要求：

- “目标”写最终要达到的结果，不把当前步骤误写成最终目标。
- “先读文件”按顺序列出，优先放规则、需求源、批准设计和实施计划。
- “确认决策”只放已经由用户或仓库证据确认的选择。
- “当前状态”使用状态标签，并指出对应文件或证据。
- “验证证据”逐条写命令与结果；失败测试注明是否与本任务相关，不能笼统写“测试通过”。
- “下一步”按依赖排序，每步含输入、修改范围、验证方式和停止条件。
- “权限边界”明确允许与禁止的动作。未知授权按未授权处理。
- “工作区”只列与交接有关的路径，并单独提示未知或用户原有变更。
- “下一 Agent 启动提示”应可直接复制使用，但仍要求先读取仓库规则和本交接文件。

### 5. 自检并交付

保存前检查：

- 是否把计划误写成已完成，或把未运行的检查写成通过。
- 是否遗漏最新用户决定、禁止动作、失败或未解决项。
- 文件路径、命令和状态是否能从当前工作区复核。
- 是否包含秘密、冗长对话、隐藏推理或无关背景。
- 下一 Agent 是否无需重读完整聊天就能开始第一项安全工作。

交付时简要说明交接文件路径、记录的当前阶段、仍未执行的高成本工作和验证状态。不要声称后续任务已经完成。

## 更新既有交接

更新不是简单追加日志。先读取全文，再用新证据替换过时状态：

1. 将已完成项从“下一步”移到“当前状态”。
2. 将新增决定同步到“确认决策”和受影响的下一步。
3. 将新失败写入“验证证据”和“阻塞项”。
4. 删除已经失效的警告，但保留仍会影响后续执行的历史结论。
5. 在“变更摘要”记录本次更新日期和关键变化。

## 禁止的交接方式

- 只写“看之前聊天继续”，让下一 Agent 重新考古。
- 把设计文档存在视为源码已经实现。
- 用“应该通过”“大概成功”替代命令证据。
- 隐去失败或中断的测试，只报告通过项。
- 把未跟踪文件、用户改动或其他 Agent 改动全部归为自己的成果。
- 在交接中嵌入密钥、cookie、token、私有地址或可执行的危险刷写命令。
- 未经授权触发 Actions、编译、提交、推送、发布、刷写或其他外部变更。

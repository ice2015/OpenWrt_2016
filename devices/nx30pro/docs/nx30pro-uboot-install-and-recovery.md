# NX30 Pro U-Boot 安装与恢复设计

状态：**设计文档，不授权刷写**。本文只规划备份、安装、回退与真机验证步骤。
本文不提供未经核实的写入命令；所有写入动作都需要用户单独、明确的授权。

- 配套事实来源：[`nx30pro-uboot-compatibility.md`](nx30pro-uboot-compatibility.md) 与
  [`../uboot/uboot-source-lock.json`](../uboot/uboot-source-lock.json)。
- 候选产物：`mt7981_h3c_magic-nx30-pro-bl2.bin`（BL2 预加载镜像）与
  `mt7981_h3c_magic-nx30-pro-fip-fixed-parts.bin`（含 BL31 与 BL33/U-Boot 的 ATF FIP 包）。
- 状态标记：候选、**未真机验证**。写入前不得把它当作可刷写发布包。
- 地址约定：本文所有分区地址都是 **NMBM 逻辑地址**，不是物理 NAND 地址。

## 1. 前置识别（只读）

在原厂系统上先收集事实，全部结果只保留在本地，不进入 Git，也不作为公开 Actions 产物：

```sh
# 固件与硬件版本
cat /etc/openwrt_release 2>/dev/null || cat /etc/os-release
uname -a

# 闪存型号、分区与启动日志
dmesg | grep -i -E "nand|spi|mt7981|boot"
cat /proc/mtd
ls -l /dev/mtd* 2>/dev/null

# MAC 与校准数据的位置（只读打印，不记录到公开渠道）
ip addr show
```

需要落档的字段：

| 项 | 记录内容 | 备注 |
|---|---|---|
| 厂商与型号 | 原厂系统显示的型号字符串 | 用于确认是 NX30 Pro 而不是 NX30 |
| 硬件修订 | 原厂标签或系统信息中的版本号 | 未知时保持 UNRESOLVED |
| NAND 型号与容量 | 启动日志中的 NAND id 与容量 | 与上游 128 MiB 假设比对 |
| 当前分区表 | `/proc/mtd` 全部输出 | 原厂分区名目前未核实 |
| 启动介质 | 启动日志中的 boot medium | 应为 SPI-NAND |
| MAC 地址 | 每个接口的 MAC | 敏感值，只本地保存 |

**不得假设某个分区编号就是整片闪存。** `/proc/mtd` 里同时存在物理闪存的主设备行与
NMBM 逻辑分区行；必须先确认哪一行描述物理闪存（master 行）、它的容量是多少，
以及哪些行是它的逻辑分区。在确认之前不要开始备份，更不要开始写入。

## 2. 备份（只读，先做后动）

备份必须在任何写入之前完成，并包含**整片闪存**与**每个关键分区**两部分：

```sh
# 先确认本机工具的选项：输出文件参数、是否跳过坏块、是否带 OOB
nanddump --help

# 整片闪存镜像，参数与设备名按上一步确认的结果填写
nanddump <本机支持的参数> <master-device> <整片镜像输出文件>

# 关键分区逐个导出，设备名用 /proc/mtd 里观察到的真实分区名
dd if=<分区设备> of=<分区镜像输出文件> bs=1M

# 校验与记录
sha256sum <备份文件列表> > SHA256SUMS
```

备份必须满足以下验收条件，缺一项就认为备份不成立：

| 条件 | 检查方法 |
|---|---|
| 备份对象是整片物理闪存 | 镜像长度与 `/proc/mtd` 中 master 行的容量一致 |
| 分区镜像长度正确 | 每个分区镜像长度与该分区容量一致 |
| 坏块与 OOB 策略已记录 | 把 `nanddump --help` 的相关选项与实际输出抄进记录 |
| 读取过程无错误 | 工具退出码为 0，日志中无 I/O 错误 |
| 校验和已生成并单独保存 | `SHA256SUMS` 与镜像分开存放 |

必须备份的对象：

| 对象 | 理由 |
|---|---|
| 整片闪存镜像 | 唯一能还原原厂分区表、NAND 坏块映射与出厂数据的副本；分区级备份**不能**替代它 |
| `bl2` | 原厂启动链第一阶段，回退时需要原样写回 |
| `u-boot-env` | 原厂环境变量，可能含 MAC 派生信息与启动参数 |
| `Factory` | 出厂数据区（2 MiB），MAC 与校准数据可能在此 |
| `fip` | 原厂 FIP 包，回退目标 |
| `ubi` | 原厂系统分区，回退目标 |
| `pdt_data`、`pdt_data_1`、`exp`、`plugin` | 若存在则必须备份；112M 布局会把这片空间划进 UBI |

备份完成后：

1. 把整片镜像与各分区镜像的 SHA-256 写进本地记录；
2. 把记录与镜像分开保存（离线介质或本地加密存储）；
3. **不要**把整片镜像或含 MAC 的分区上传到公开 Actions artifact，也不要提交 Git；
4. 确认存在一条**不依赖候选启动链**的恢复途径（见第 3.3 节），否则不要进入写入阶段。

若整片镜像无法生成（例如原厂系统缺少相应工具），记录该事实并保持 UNRESOLVED，
不要用分区级备份冒充完整备份。

## 3. 三种场景必须分开

### 3.1 已运行候选启动链时的升级

前提：设备当前已经能启动到本候选 U-Boot。

| 入口 | 证据 | 写入对象 |
|---|---|---|
| 网页恢复入口 `http://192.168.1.1/` 上传 `fip` | `failsafe/failsafe.c` 的 `upload_handler` 接受 `fip`；`board/mediatek/common/bootmenu_mtd.c` 的 `write_fip` 写入 `fip` 分区并回读校验 | `fip` 分区（NMBM 逻辑 `0x380000`，2 MiB） |
| 串口 U-Boot 命令 `mtkupgrade fip` | 启动菜单项 "Upgrade ATF FIP" → `cmd_mtkupgrade.c` | `fip` 分区（NMBM 逻辑 `0x380000`，2 MiB） |
| 网页恢复入口上传 `bl2` | `write_bl2` 写入 `bl2` 分区；上传前会做 BL2 校验 | `bl2` 分区（NMBM 逻辑 `0x000000`，1 MiB） |

限制（来自源码，必须写进操作说明）：

- FIP 上传**不做**结构校验（`CONFIG_MTK_UPGRADE_FIP_VERIFY` 未开启），
  只做写入后回读校验；回读校验只能证明“写入的字节与上传的一致”，
  **不能**证明上传的镜像本身正确，镜像的正确性只能靠构建报告与内容识别来保证。
- BL2 上传**会**做 BL2 校验，且要求启动介质匹配 `SPINAND!` 头（本板为 SPI-NAND）。
- 网页恢复入口的地址是 `192.168.1.1`（U-Boot 侧固定 `CONFIG_IPADDR`），端口 80；
  复位键长按进入的机制在源码中确定（`glbtn` 计数 4 秒），实际按键时序保持 UNRESOLVED。
- 这两个入口只能覆盖启动链与系统镜像，**不能替代**独立恢复路径，也不能代替原厂备份。

### 3.2 从原厂系统首次安装候选启动链

**状态：UNRESOLVED。** 原厂启动链是否提供可用的安装入口没有证据；
候选启动链自己的网页/串口入口只有在原厂 BL2 与 FIP 仍然可用时才有意义，
而一旦首次写入失败，就没有软件手段回到原厂。因此：

- 在第 3.3 节的独立恢复路径被证明之前，**不执行**首次安装；
- 不借用其他机型的安装命令，不把“原厂系统自带恢复”当作既有事实。

### 3.3 启动链不可启动时的恢复

**状态：UNRESOLVED。** 网页恢复入口与串口 `mtkupgrade` 都要求设备能启动到 U-Boot；
BL2 损坏时设备进不了 U-Boot，这两条路径同时失效。可接受的独立恢复途径
（例如原厂恢复流程、外部编程器或另一台可引导设备）在没有真机证据前不给出任何命令。

**停止条件：在独立恢复路径被证明、并且第 2 节的整片备份验收通过之前，不得进行任何写入。**

## 4. 刷写前审阅清单（单独交付给用户）

实际写入前，必须把下面这张表连同镜像的 SHA-256 一起交给用户确认，用户明确授权后才执行：

| 项 | 内容 |
|---|---|
| 目标文件 | `mt7981_h3c_magic-nx30-pro-fip-fixed-parts.bin`（FIP）、`mt7981_h3c_magic-nx30-pro-bl2.bin`（BL2） |
| 文件 SHA-256 | 取自构建产物的 `SHA256SUMS` 与 `build-report.json` |
| 写入对象 | `fip` 分区（NMBM 逻辑 `0x380000`，2 MiB）/ `bl2` 分区（NMBM 逻辑 `0x000000`，1 MiB） |
| 写入方式 | 网页恢复入口上传，或串口 `mtkupgrade fip`（仅适用于第 3.1 节的场景） |
| 独立恢复路径 | 必须已证明可用；否则不写入 |
| 回退路径 | 用第 2 节的 `bl2`、`fip`、`u-boot-env` 备份原样写回；该路径同样依赖可启动的 U-Boot |
| 数据损失范围 | 写入 FIP/BL2 本身不改写 `Factory` 与 `ubi`；但随后首次启动 112M 系统会按 112M 布局擦除原厂的 `pdt_data`、`pdt_data_1`、`exp`、`plugin` 区域 |
| 系统侧副作用 | 所选系统启动时若 `Factory` 偏移 4 的前两字节为 `00-0c`，会把派生出的 Wi-Fi MAC 写回 `Factory` 偏移 4 |
| MAC 供给 | 所选系统从 `pdt_data_1` 读取 WAN MAC，而 112M 布局没有该分区；在固件侧解决前不得成对测试 |
| 风险 | FIP 校验关闭，写入错误镜像只能靠回读校验发现；BL2 错误会导致设备无法启动 |

## 5. 回退

1. 回退输入：第 2 节备份的 `bl2`、`fip`、`u-boot-env` 原始镜像及其 SHA-256；
2. 回退写入方式：与安装相同的两条入口（网页恢复入口或串口 `mtkupgrade`），
   前提是设备仍能启动到 U-Boot；**不可启动**时只能使用第 3.3 节的独立恢复途径；
3. 回退后必须重新做一次冷启动与启动日志检查；
4. 原厂系统的完整恢复（例如原厂云端或本地恢复流程）在没有真机证据前保持 UNRESOLVED，
   **不得**借用其他机型的恢复命令或宣称可以一键回到原厂。

## 6. 真机验证（授权后执行）

写入并重启后，按顺序验证，每一步都留下原始输出：

| 步骤 | 观察点 | 通过标准 |
|---|---|---|
| 冷启动 | 串口启动日志 | U-Boot 起来后识别出 `bl2`、`u-boot-env`、`Factory`、`fip`、`ubi`，且 `ubi` 为 112 MiB |
| NMBM | 启动日志中的 NMBM 段 | 坏块映射正常，无重复块告警；实测逻辑容量不小于 `0x7580000` |
| MAC | 各接口 MAC | 与原厂备份一致；系统侧的 `pdt_data_1` 依赖已解决 |
| 无线校准 | 射频校准读取 | 与原厂备份一致，无校准缺失告警 |
| 出厂数据 | `Factory` 偏移 4 | 与备份比对，记录系统是否改写了该位置 |
| 复位按钮 | 长按 reset | 按源码机制进入网页入口；实际时序记录下来 |
| 网页恢复入口 | 进入 failsafe 后访问 `http://192.168.1.1/` | 页面可打开，能列出可上传的启动链镜像 |
| 最小系统启动 | 启动最小可启动系统 | 内核与 rootfs 正常挂载 |
| 匹配工厂镜像 | 网页安装与所选系统匹配的 factory 镜像 | 写入成功并能启动 |

验收方式：**不使用**主动断电写入作为验证手段。所有写入都走正常上电流程与官方入口。
任何一步失败都先回退，再分析，不得继续叠加写入。

## 7. 未决项（UNRESOLVED）

1. 原厂系统的真实分区名、master 行容量与整片备份的可获得性；
2. 原厂系统自身的恢复入口（云端或本地）以及任何**独立**于候选启动链的恢复途径；
3. NAND 芯片型号、容量与坏块布局；
4. MAC 与无线校准数据的确切存放位置（`Factory` 分区的偏移）；
5. 所选系统在 112M 布局下的 WAN MAC 供给方式（`pdt_data_1` 不存在）；
6. 进入 web failsafe 的按键时序；
7. 候选 U-Boot 在真机上的启动行为与 112M 系统的兼容性；
8. 工具链确切版本与产物逐字节可复现性。

在第 6、7、8 项完成前，本设备目录内的 U-Boot 产物只能标记为“候选、未真机验证”。
